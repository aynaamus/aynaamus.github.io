BTGI — Bitcoin Transaction Graph Investigator

A local graph-analysis tool for the Elliptic Bitcoin data set: validated ingestion, bounded directed-path exploration, explainable structural alerts and a case workflow.

Not a validated illicit-transaction detector. On the held-out period the structural rules performed worse than the base rate. Risk scores measure structural prominence, not the probability of criminal activity.

Investigative problem

Transaction graphs are explored one neighbourhood at a time: who sent to this transaction, who sent to them, and whether the pattern is unusual. BTGI makes that exploration bounded and reproducible, and keeps every rule hit traceable to the specific edges behind it.

Architecture and tools

  • DuckDB stores transactions, features, labels and edges, with ingestion runs and source-file hashes, detection runs, alerts and evidence, and cases.
  • Neighbourhoods and paths are built with one bounded SQL query per hop (depth up to 4, with node and edge caps, flagged when truncated). The full graph is never loaded for exploration.
  • Streamlit and Plotly with five views, and a command-line interface for every analytical step.

Data and scale

The Elliptic Data Set (Weber et al., 2019; CC BY-NC-ND 4.0): 203,769 transactions and 234,355 directed edges across 49 time steps, with 166 anonymized features. Labels are illicit, licit or unknown, and unknown is never treated as licit. The data has no addresses, owners or amounts, and is not redistributed.

Engineering capabilities

  • Transactional, idempotent ingestion with recorded file sizes and SHA-256 hashes; source files are never modified.
  • SQL integrity checks: totals, duplicates, missing nodes, self-loops, missing features, degree distributions and connected components (the 49 components coincide with the 49 time steps).
  • Three topology-only, label-free rules: high degree, concentrated fan-in or fan-out, and high two-hop reach. Thresholds come from reference steps 1–34 only.
  • Each rule hit stores the observed value, threshold, the exact evidence total and up to 25 supporting edges, and the complete set can be retrieved on demand.
  • Case workflow with an audit row for every change. Dispositions describe a review outcome and never assert criminal activity.

Testing and verification

82 pytest test functions cover ingestion, graph checks, detection, evaluation and exploration, the alert queue and plots, cases and the application. The evaluation was run once on a configuration fixed beforehand and is reported unchanged.

Measured performance

Engineering

Validated graph, bounded exploration, evidence traceable to edges, audited case workflow.

Below the base rate. Precision of 1.15% is lower than the 6.50% known-label illicit prevalence.

Limitations

  • Graph profiling examined structural statistics for all time steps, including the held-out ones, before the rules were fixed, so the evaluation is not a fully untouched out-of-sample test.
  • The evaluation is retrospective on complete per-step snapshots, not real-time detection.
  • The two-hop rule often fires on transactions that are merely adjacent to a hub.
  • The data is anonymized, so nothing here supports attributing a transaction to a real wallet, person or organization. Paths show topology, not intent, ownership or laundering.
  • The audit trail is append-only through the application only; the database file has no tamper evidence.
