ATIS — Account Takeover Intelligence System

A local toolkit for investigating authentication anomalies: leakage-safe detection rules, traceable evidence, bounded account–IP relationship analysis and an audited case workflow.

Not a validated security control. On the held-out period the rules detected 0 of 65 labeled takeover events. Alerts are behavioural anomalies, not confirmed account takeovers. The project is an exercise in explainable, leakage-safe investigation tooling.

Investigative problem

Login data is high in volume and ambiguous: eight failed logins followed by a success may be a user retrying a password or someone guessing it. ATIS records exactly what each rule saw, separates evidence available at alert time from later events, and leaves the conclusion to the analyst.

Architecture and tools

  • DuckDB for ingestion, causal SQL rules, alerts, evidence and cases.
  • Separate modules for ingestion, validation and profiling, detection and calibration, evaluation (the only detection-side module that reads the label), relationship queries and the case workflow.
  • Streamlit with local Plotly graphs: Overview, Alert Queue, Investigation, Relationships and Detection Performance.

Data and scale

The Login Data Set for Risk-Based Authentication (Wiefling, Jørgensen, Thunem and Lo Iacono, 2022; CC BY 4.0): 31,269,264 events across 4,304,857 accounts, February 2020 to February 2021, with 141 labeled takeover events. Feature values are synthesized from real login patterns. The dataset is not redistributed.

Engineering capabilities

  • Ingestion validates the schema before any write, checks disk space, runs in one transaction and treats a re-ingest of the same file (SHA-256) as a no-op. Malformed values are counted, never imputed.
  • Three rules: failed-login bursts per account, first-seen browser, OS or device for an established account, and many accounts on one IP within an hour. Each uses only the alerted event and earlier events.
  • Thresholds are calibrated on an unlabeled reference period to fixed alert budgets.
  • Every alert stores its evidence and up to 50 supporting source events. Events after an alert are shown as retrospective context the rule never saw.
  • Relationship queries are bounded, with hard caps. Shared IPs or devices are presented as co-occurrences, not as evidence of ownership or coordination.
  • Cases with append-only audit rows written in the same transaction as each change.

Testing and verification

82 pytest test functions cover ingestion, validation, rules, the detection system, case and query logic, and the application. Predictions are stored before evaluation, recall is reported with Wilson 95% intervals, and no threshold was changed after seeing held-out labels.

Limitations

  • Of all 141 labeled events, 101 occur within an account’s first five events, where history-based rules cannot judge (a post-hoc diagnostic; nothing was tuned on it).
  • The new-environment rule makes up about 97.6% of rule firings and is a weak signal.
  • Account-level recall (16 of 63) is retrospective, not real-time detection.
  • Extreme class imbalance and synthesized IPs, geography and devices. The dataset authors advise against using it for production intrusion detection.
