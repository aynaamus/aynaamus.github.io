CRIE — Corporate Relationship Intelligence Engine

An investigation workbench for reported corporate relationships. It records what each source says, how the investigator assessed it, and produces reports whose evidence can be checked later.

Investigative problem

Public corporate data says less than it appears to. In GLEIF’s Level 2 data, legal entities report the parents that consolidate them in their accounts. That is useful, but it is largely self-reported, it is not evidence of ownership or control, and when two files differ the data alone does not say whether, or when, anything changed.

CRIE is built for the work that follows: opening a case on one relationship, registering the documents found, transcribing claims with their location, recording how each source was reviewed and whether sources are independent, and producing a report that a reviewer can verify.

Architecture and tools

  • Python 3.12 domain logic and command-line tools (src/).
  • Streamlit interface with four pages: Investigate, My Investigations, Published Investigations and Methodology.
  • MySQL as the system of record. Audit rules are enforced in the database: append-only tables whose triggers reject UPDATE and DELETE, supersession checks and foreign keys.
  • A hardened streaming XML parser for GLEIF LEI-CDF and RR-CDF files. Each file is hashed and counted in one pass and imported in a second, in restartable, leased batches with recorded coverage.

Data

GLEIF Legal Entity Identifier and relationship records (published under CC0). Every GLEIF file is kept as an observation with its SHA-256, import batch and coverage, so the same relationship can be compared field by field across files. Records with failing LEI check digits are quarantined: kept as evidence of what the file said, never promoted to trusted entities.

The public repository contains no bulk GLEIF data and no private research records. Its demonstration case uses synthetic companies, documents and GLEIF files.

Engineering capabilities

  • Evidence lineage. Claim corrections and restorations add new versions, and the original stays recorded. Source reviews, independence assessments and identity mappings are superseded, never overwritten.
  • Corroboration rules. Agreement counts as corroboration only between sources whose independent origin the investigator has recorded. Republished or related sources never corroborate each other.
  • Manual identity resolution. Claim subjects are mapped to legal entities only by the investigator (MAPPED, AMBIGUOUS, NO_LEI, UNRESOLVED); a matching name is a hint, not proof.
  • Verifiable reports. Each report is rendered from an evidence snapshot read in one consistent transaction, stored with its hashes and code version, and later checked for integrity (files unchanged), reproducibility (same output from the same code) and currency (evidence unchanged).
  • Ownership and publishing. Each investigation belongs to the user who opened it, every write checks ownership, and only a verified, registered report can be published.

Testing and verification

The repository has 943 pytest tests. The 782 unit and interface tests pass without a database. The other 161 are MySQL integration tests, run on request against dedicated test databases. They check the database identity before writing and remove the synthetic rows they create. The deployment procedure was rehearsed end to end on MySQL 8.4.13.

Limitations

  • Consolidation is not ownership, and the network is a sample, not a complete ownership tree.
  • CRIE does not decide whether a relationship is true, who controls a company, or whether anything is wrong. Its corporate-change determination is always “insufficient evidence”.
  • An “intact” report means its files match their hashes, not that the disclosures are correct.
  • Claims are entered one at a time, and the analyst’s case assessment does not yet keep its history. Sign-in through an external identity provider is implemented but has not been verified with a real provider.
