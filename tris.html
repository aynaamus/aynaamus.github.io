Intelligence systems · Transaction monitoring

TRIS — Transaction Risk Intelligence System

A local transaction-monitoring and investigation workbench: SQL detection rules with stored evidence, account-network exploration, held-out evaluation and an audited case workflow, built on synthetic mobile-money data.

All data is synthetic. Alerts are suspicious-activity indicators. They are not confirmed fraud or evidence of money laundering, and the fraud label is a simulator output, not a real-world finding.

Investigative problem

Transaction monitoring produces alerts that an analyst has to explain and act on. TRIS explores how much of that work can be made transparent: each alert stores the rule, threshold, observed value and linked transactions, and every case decision is written to an audit trail.

Architecture and tools

  • DuckDB holds everything in one file: transactions, ingestion log, thresholds, alerts and evidence, and the case tables.
  • Detection runs as SQL inside DuckDB; nothing is loaded into Python memory.
  • NetworkX and Plotly for bounded account neighbourhoods, with HTML and GraphML export.
  • Streamlit interface with five views: Overview, Alert Queue, Alert Investigation, Account Network and Detection Performance. It contains no business logic.

Data and scale

PaySim, a mobile-money simulator calibrated on aggregated real logs (Lopez-Rojas, Elmir and Axelsson, 2016): 6,362,620 transactions, 8,213 labelled as simulated fraud. The dataset is not redistributed.

Leakage controls are enforced in code: the fraud label is read only by the evaluation module, the simulator’s own fraud flag is never used, and balance columns are excluded from detection.

Engineering capabilities

  • Idempotent, transactional ingestion matched by SHA-256, with SQL validation.
  • Three explainable rules: large amount against per-type reference percentiles, destination concentration, and rapid onward movement of 80–100% of an inflow within six simulated hours.
  • Thresholds come only from a reference period (steps 1–400); rerunning detection takes about two seconds and never touches cases, notes or audit history.
  • Alert queue filtered, sorted and paginated in the database; only one page is ever loaded.
  • Case workflow (open, in review, escalated, closed) with dispositions, findings and notes. Every change is written to an append-only audit table in the same transaction.

Testing and verification

44 pytest test functions cover ingestion, detection, networks, the investigation workflow and the application. The evaluation uses a chronological split, and nothing was tuned against held-out labels.

Limitations

  • Rule B fires only in the simulator’s start-up period and nothing in the held-out period.
  • Rule C has little to work with: almost every origin account appears once, leaving one qualifying pair in the held-out period, which was a false positive.
  • PaySim fraud is generated by simulator scripts, so these figures say little about real-world fraud or anti-money-laundering detection.
  • Single-user and local, with no authentication. The audit trail is append-only through the application, not through database permissions.
